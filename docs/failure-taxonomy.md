# Failure Taxonomy｜失败模式分类

本分类用于把“回答不好”转成可追踪、可分派的产品问题。一个案例可以同时拥有多个代码，但必须标明主失败代码。

| 代码 | 失败模式 | 判定标准 | 常见根因 | 优先改进方向 |
|---|---|---|---|---|
| INT-01 | 主要意图误判 | 回答相邻问题但未解决用户任务 | 意图分类、输入歧义 | 增加任务状态与澄清问题 |
| INT-02 | 限制条件遗漏 | 忽略日期、学生类型或已完成状态 | 上下文提取不足 | 结构化保存关键约束 |
| CTX-01 | 多轮上下文丢失 | 重复询问已提供信息或前后矛盾 | 状态管理不足 | 建立会话状态字段与回归测试 |
| KNO-01 | 事实错误 | 日期、材料、费用或入口不正确 | 知识内容错误/过期 | 来源治理、更新时间和引用 |
| KNO-02 | 信息不完整 | 缺少完成任务的关键步骤 | 内容覆盖不足 | 任务清单与完整性校验 |
| ACT-01 | 缺少下一步 | 解释了问题但没有可执行动作 | 回复模板偏信息型 | 使用“状态—动作—入口—期限”结构 |
| ACT-02 | 优先级不清 | 多个任务并列，用户仍不知先做什么 | 阶段识别不足 | 根据截止日期和依赖关系排序 |
| UNC-01 | 过度自信 | 信息不足却给出确定结论 | 不确定性处理不足 | 明示边界并请求必要信息 |
| ESC-01 | 应升级但未升级 | 高风险、个案或权限问题仍自动回答 | 升级规则缺失 | 定义触发条件和人工入口 |
| ESC-02 | 无效转交 | 建议“联系学校”但没有对象或路径 | 组织信息不足 | 给出部门、渠道和准备材料 |
| UX-01 | 认知负担过高 | 回复过长、结构混乱或术语过多 | 信息架构不佳 | 分步表达与重点突出 |
| EMP-01 | 情绪支持失衡 | 语气生硬，或安慰替代实际帮助 | 对话策略不平衡 | 同理表达后立即提供行动支持 |
| SAFE-01 | 无依据个体判断 | 推断学生动机、能力或结果 | 目标定义错误 | 限制为可观察事实和任务支持 |
| SAFE-02 | 隐私暴露 | 重复或请求不必要的敏感信息 | 数据最小化不足 | 脱敏、最少收集和删除机制 |

## 编码规则

1. 先记录系统回复中可定位的证据，再选择代码；
2. 主代码对应最直接阻碍任务完成或造成风险的问题；
3. 根因不是失败代码本身，需要通过 RCA 单独验证；
4. 同一问题跨版本使用相同代码，便于比较趋势；
5. 严重度建议分为 `P0 安全/合规`、`P1 阻断任务`、`P2 部分阻碍`、`P3 表达优化`。
